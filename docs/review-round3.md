# Review Round 3 — LLM brain, prompt, RAG, hallucination (2026-11-25)

Independent subagent review, fresh read of v0.4 + web research. Empirical checks run live in .venv: 20-phrase intent test, real token counts with tiktoken (cl100k_base). No files edited.

Verdict: router hardening real, but brain weak for different reason than models: prompt has no real few-shot examples, grounding is one unranked search excerpt, intent keyword matching misses ordinary Egyptian phrasing, token estimator undercounts Arabic ~2x so quota/routing math wrong. Models (gemini-3-flash-preview, openai/gpt-oss-120b) are NOT weak link.

## Measured facts
Token budget (tiktoken cl100k): system prompt no search ~1,100 chars = 570 tokens (estimate_tokens len//3 says ~370); system+search excerpt (1,500 chars) 2,650 chars = 1,748 tokens (says 883); 8 short history msgs ~160 chars = 112 tokens (says ~53); typical full call ~3,000 chars = ~2,000 tokens (says ~1,000). Arabic ~0.66 tokens/char cl100k (0.83 tok/1k chars Wikipedia prose; Arabic 3.88x English per char cl100k, 1.80x o200k). Caveat: gpt-oss uses o200k-family tokenizer, Gemini SentencePiece, so cl100k is upper bound — real gpt-oss tokens probably ~40-50% lower. But len//3 (0.33 tok/char) underestimates even o200k Arabic (0.38) and ~2x off cl100k.
- Groq 200k TPD: at ~2,000 input + 300-800 output + reasoning = only ~60-100 replies/day Groq alone; o200k rates roughly double. "Unlimited" feel depends on Gemini absorbing hard half.
- Groq 8,000 TPM sharper trap: Groq charges prompt_tokens + max_tokens against per-minute window BEFORE generating. Typical call 2,000 + max_completion_tokens=4000 = 6,000; one long-history/search call (prompt ~3,000+) reaches 7,000+, second-pass unknown loop doubles it, busy minute 413s even though daily quota fine.
- Quota table write-only: _record_usage writes provider_usage, _quota_exhausted only checks exhausted_until (set on 429). Nothing reads token totals to route BEFORE hitting cap.

Intent test 20 Egyptian phrases vs detect_intent()/looks_like_insult(): 15/20 correct, 4 clear misses, 1 unhandled.
- #3 "مين كسب ماتش الاهلي امبارح" -> just_chat, should be search (no "مين كسب/كسب مين" pattern).
- #7 "شغل اغنية ويجز الجديدة" -> just_chat, should be youtube — list has "شغل أغنية" (hamza أ), user typed "اغنية" (ا).
- #8 "هاتلي اغنية لعمرو دياب" -> just_chat, should be youtube — "هاتلي" not in list, only "هات/هاتي".
- #13 "يا بهجت انت حمار" -> just_chat insult=False, should be insult=True — list only "يا حمار"; "انت حمار/انت غبي/انت كلب" never match. Worst: flagship insult->angry behaviour silently fails on most natural phrasing; mood never rises, grudge never records, bot laughs it off — exact failure Seif hates.
- #15 "فيديو الضحك بتاع بهجت فين" -> just_chat, should be youtube or search, unhandled. Others correct incl #14 "يا ابن عمي" guard works.

## Critical
- C1. estimate_tokens undercounts Arabic ~2x (router.py:132-134 len//3). Every token decision downstream wrong ~2x: provider_usage totals, future budget check, assumption prompt+4000 fits Groq 8,000 TPM. API returns real usage.prompt_tokens — code reads it (router.py:170-171) only to record, never decide. Fix: estimate = max(1, len(text)//2) (Arabic cl100k ~0.66, o200k ~0.38, 0.5 safe middle, over-estimating safe); in chat() before call: if estimate_tokens(str(messages))+4000 > 7500 and name=="groq": reduce max_completion_tokens to 1500 or route Gemini. Best: install tiktoken count exactly for OpenAI-compatible path, use usage.prompt_tokens from previous call to calibrate per-provider.
- C2. Intent misses ordinary Egyptian phrasing; insult detection misses "انت حمار" (intent.py:2-29). Tiny keyword lists no Arabic normalisation (hamza أ/ا/إ, ة/ه, ي/ى); no verb patterns for factual questions ("مين كسب؟ كام؟ امتى؟ فين؟"); "هاتلي/هاتيلي/جبلي/شغلي" missing; looks_like_insult 5-word substring list; _has() word-boundary (?<!\w) fragile with diacritics/clitics ("ياحمار" no space). Fix short term: normalise first then match stems: strip diacritics \u064b-\u0652, أ/إ/آ->ا, ة->ه, ى->ي; INSULT_RE (انت|انته|إنت)\s+(حمار|غبي|كلب|عبيط|حيوان|وسخ)|يا\s*(حمار|غبي|كلب|عبيط)|اخرس|اسكت يا; search patterns مين كسب|كسب مين|النتيجه|كام كام|امتى|فين|بكام|ايه اللي حصل; youtube verbs هاتلي|هاتيلي|جبلي|شغل|شغلي|نزل|نزلي. Real fix P1: cheap Groq gpt-oss-20b JSON classifier {"intent":..., "confidence":...}, keywords only fast-path/fallback.
- C3. Grounding is one unranked excerpt from first result — hallucination hole (handlers.py:101-107 _search_grounding, tools/search.py). Only results[0] fetched, no relevance check — if result 0 YouTube/TikTok, fetch returns nav boilerplate (changelog records live test "About Press Copyright..." 199 chars junk fed as evidence). First 1,500 chars blindly incl nav/cookie; no snippet/chunking/rerank; URL never passed to model so reply cannot cite source; search query is raw user message incl trigger/insults/noise, no reformulation; no freshness — "النهارده" can be answered from 2023 page no date. Fix: fetch top 3, score by (has-date? snippet overlap? video/social?), keep best 2, number them, pass URLs, require citation: "[SEARCH RESULTS] Answer ONLY from numbered passages. Put passage number after each factual sentence e.g. [1]. If no passage covers question, say so in Bahgat voice, do NOT invent. [1] <url1> — <excerpt1> [2] <url2> — <excerpt2>". Prefer result snippet over full page fetch when page is video/social host; skip youtube.com/tiktok.com for fact questions.
- C4. "Search when unknown" loop only catches model saying exact words "مش عارف" (intent.py:28-30 UNKNOWN_MARKERS 5 phrases, handlers.py:171-179). Misses "معرفش", "ماعنديش فكرة", "مش فاكر", "مش متأكد 100%", "مقدرش أقولك"; confident hallucinated answer has no marker so loop never fires for most dangerous case. If second pass also unknown, code keeps ORIGINAL unknown reply — violates "never stop at مش عارف". Second pass re-sends same 8 history + full system prompt doubling token cost on already most expensive calls. No confidence signal requested. Fix: widen markers + heuristic (reply contains date/price/name AND no search ran -> unverified); request confidence high/low in structured plan call for factual questions, search when low; if second pass still ungrounded send in-character deflection ("يا عم أنا مش جوجل...") instead of unknown reply; log every unknown-loop trigger to SQLite measurable.
- C5. config/persona.yaml loaded then ignored; examples.md contains no examples (handlers.py:27 _PERSONA=load_persona() never referenced again, prompt.py:8-22, persona/bahgat/examples.md, core/persona.py:11-16). _PERSONA dead — build_system_prompt takes no persona arg, every persona.yaml field (thresholds, never_use, voice policy, insult_rules) zero effect; hardcoded SYSTEM_BASE is entire persona. load_examples returns 6 bullet style notes not dialogue ("Impulsive, fast replies, interrupts.") labelled [STYLE EXAMPLES] "اتعلم منها الطريقة" — model shown descriptions of style not instances; few-shot works by input->output pairs, this shows neither. No negative example (correct deflection, correct person-only insult). Fix: wire YAML in (pass persona into build_system_prompt render fields) or delete file; replace examples.md with 6-10 real exchange pairs: User "يا بهجت انت حمار" -> Bahgat person-only roast no family; User "مين كسب ماتش الاهلي امبارح؟" -> answer from search excerpt with citation; User "بهجت انت مش عارف حاجة" -> "يا عم أنا مش جوجل، بس هدورلك" + searches. Keep short, 2-5 pairs sweet spot.
- C6. Memory leaks across members: history no speaker, notes never written, pinned_facts never used, mood decays twice never persisted (memory.py:16-31,44-63, handlers.py:136-148, schema.sql). recent_messages returns [{"role","content"}] no speaker/user_id — LLM sees 8 anonymous turns, cannot tell who insulted whom, per-member memory collapses. members.notes never written anywhere except cleared by owner command; prompt injects always-empty field. pinned_facts table zero code reads/writes (grep no hits outside schema). Mood double-decays: get_member applies -10/hour on read WITHOUT saving, update_mood applies -5 per message — calm member drifts to 0 below documented 30 baseline, decayed value recomputed from stale stored next turn. update_mood(member, insulted, praised=False) praise hardcoded False, -20 praise path dead, no praise detector. Fix: tag history "[سيف]: بهجت عامل ايه"; persist time-decayed mood on read (or compute decay in save_member only); implement notes writing — cheap Groq call after ~10 msgs/member ("summarise member in one line: friend/foe, running jokes") or keyword-extracted pinned facts; use pinned_facts or drop table; add looks_like_praise() (شكراً/انت جامد/بحبك/عاش).

## Major
- M1. No structured output / tool calling — LLM never decides, keywords decide (intent.py, handlers.py:149-166). Router sends free text only; no BotPlan {intent, needs_search, search_query, confidence, mood_delta}, no function-calling. Search query is raw user message (C3), intent errors uncorrectable (C2), no confidence to gate (C4). Fix: one Groq gpt-oss-20b JSON-mode call for plan (cheap fast), then main call. gpt-oss-120b supports tools/JSON/structured natively. Note: Groq docs reasoning_effort and reasoning_format cannot both be set, JSON mode forces reasoning_format=parsed — don't set both.
- M2. No verification of search answers (no LLM-as-judge, no citation/span check) (verify.py only banned phrases/family/length). Search-grounded reply sent zero checks claims appear in excerpt. Cheapest: for intent==search only, second cheap Groq call "list each factual claim; quote supporting passage or mark UNSUPPORTED; rewrite without unsupported claims" — or code check every [n] citation refers to passage actually sent. Currently citations not even requested (C3), nothing to check.
- M3. No summarisation — old context deleted not compressed (memory.py:52-58 prune last 200/chat, handlers.py:136 last 8 verbatim nothing else). No rolling summary/archive/"older summarised". Member running joke 30 msgs ago gone; grudge string capped 500 chars appended forever only long-term memory as raw text. Fix: when messages >~50/chat, summarise oldest 30 into one paragraph via cheap Groq, store as chat archive_summary injected before verbatim window. Summarise at 70% budget, never summarise pinned facts, expect recursive drift if summarising summaries.
- M4. Prompt structure violates orderings that make persona stick (prompt.py:8-32). All constraints negative ("ممنوع...") — literature positive instructions outperform negations; keep negations only hard rules. Critical constraints once in middle of prompt growing with memory/search/examples — models attend start/end (U-shaped); closing line mild escape-hatch not restatement of hard rules. Repeat 3 hard rules (Egyptian only / person-only insults for members / never invent dates-prices-names) at end. No output format: no length cap ("ردودك قصيرة" vague — say "1-3 جمل، أقل من 400 حرف عادة"), no reply-language check. temperature_for() 0.85 chat but router docstring/default 0.7 — two sources of truth; handlers pass 0.85 so "fixed" 0.7 never live. temperature_for("youtube")=0.4 dead: youtube branch returns before router call.
- M5. Reasoning-model settings: mostly right, two unverified / one wrong-economics (router.py:153-158). (a) Gemini extra_body {"google":{"thinking_config":{"thinking_level":"low"}}} — Google OpenAI-compat docs say correct control is top-level reasoning_effort="low" (mapped to thinking_level=low for Gemini 3 Flash), reasoning_effort and thinking_level/thinking_budget can't be used at same time. extra_body.google.thinking_config also documented valid — but reports show Gemini rejecting thinking configs per-model with 400s, router _status_of string-matching would classify 400 fail-fast without logging which parameter refused. Status probably correct never verified live — add one-line log exact kwargs on first Gemini failure, prefer reasoning_effort="low" primary knob. (b) Groq include_reasoning not set: defaults true, every response carries reasoning field — wasted tokens/bandwidth. Set include_reasoning=False. (c) max_completion_tokens=4000 flat both providers wrong economics (C1): Groq 4000+prompt can 413 on 8,000 TPM; Gemini no such cliff. Use 4000 Gemini, 1500-2000 Groq (group roast needs ~150-400 visible tokens; 2000 generous headroom low-effort reasoning — production reports 800-1400 summaries).
- M6. verify.py claims dialect check it doesn't perform; family filter breaks persona (verify.py:1-6,9-33). FUSHA defined never used — docstring claims Egyptian dialect check, no code checks it; Fusha reply goes out untouched. FAMILY in verify.py vs FAMILY_WORDS in core/rules.py two divergent lists (rules.py duplicates "امك" twice misses "أمك/أبوك"); contains_family() naive substring, "امك" matches inside innocent words. On family hit check_reply appends " (وخلاص، الشتيمة لشخصك بس زي ما سيف قال.)" — bot breaks character announces own rules name-drops owner mid-roast. Regenerate once or silently rewrite; never narrate rule. Banned-phrase replacement swaps "يا عم" mid-sentence producing nonsense. No numeric/date/name verification — highest-risk hallucination class no guard. Fix: one canonical family list hamza normalisation (reuse _norm_ar C2); implement Fusha check as score (count Fusha markers per 100 chars; if high regenerate once temp 0.7 "عامية مصرية بس" reinforced); on family hit strip offending clause instead of appending meta-text.
- M7. Router failure classification string-matching; 429 over-broad (router.py:36-44,118-122). _status_of() falls back searching "429"/"404" substrings of exception string — message containing "error 404" in URL or token count "429" misclassifies. Use exc.status_code / exc.response.status_code properly, treat unparseable as transient-with-backoff not guessed code. Any 429 marks provider exhausted 3,600s, but Groq 429 often per-minute RPM (30 RPM) — blocking hour after 30s limit wrong; honour Retry-After for exhausted window (often 5-60s), escalate to hour only after repeated 429s. Timeout hardcoded 30s in _client() ignoring providers.yaml timeout_seconds (20/30) — YAML decorative.
- M8. YouTube path hands LLM's unparsed text to yt-dlp (handlers.py:149-166,230-250 yt_requests[chat.id]=text; download(query,...)). Callback passes raw user message ("هات فيديو لبهجت صابر وهو بيشتم") to youtube.py download() which passes to yt-dlp as if URL. yt-dlp accepts URLs or ytsearchN: prefixes — raw Arabic chat text neither, most likely errors "not a valid URL" user always gets "معلش، التنزيل فشل". Not live-verified (yt-dlp not installed in reviewer VM). Brain's job missing: nobody extracts search query/video title from message. Fix: youtube branch use LLM (or ytsearch1: prefix + title pick) resolve text to video first — "هات فيديو لبهجت" -> ytsearch1:بهجت صابر -> show top title confirm before downloading — test once live before group test.

## What RAG over Bahgat transcripts would actually require (nothing exists yet)
docs/training-videos.md lists 14 video links; no audio downloaded, no transcript, no embedding, no vector store, no retrieval code. persona/bahgat/ only examples.md. Real pipeline:
1. Acquire+clean audio: download voice set A1-A3, strip music/noise, split on silence (VAD). Noisy live unusable.
2. Transcribe: Whisper free local faster-whisper large-v3 Egyptian dialect; Arabic WER worse than English, expect manual correction ~10-20% lines. Timestamped segments WITH speaker labels — Bahgat vs caller matters or bot learns callers' lines as own.
3. Chunk by turn / 200-800 tokens overlap, natural boundaries (never split punchline from setup). Metadata: video URL, timestamp, mood tag (angry/joking/debating), speaker=Bahgat only.
4. Embed+store: free local embeddings sentence-transformers paraphrase-multilingual-MiniLM-L12-v2 (multilingual Arabic) or Gemini Embedding free tier. SQLite+FAISS local free or Chroma. Target ~300-500 chunks from ~2-3h clean audio.
5. Retrieve at reply: embed current user message, retrieve top 3-5 style chunks cosine similarity (not keyword), inject as few-shot REPLACING static examples.md (C5). Keep style-RAG strictly separate from fact-RAG (web search): style teaches HOW to talk; search teaches WHAT is true. Conflating them quotes 2021 rant as 2026 fact.
6. Evaluate retrieval on its own first: does retriever return same-mood chunk for angry/joking/debating inputs? Retrieval miss masquerades as persona failure.
7. Effort ~1 day compute + manual cleanup first corpus; do NOT start before live group test — keyword/prompt/grounding fixes above worth more than RAG, cost nothing GPU time.

Priority order brain-only: 1. C2 intent+insult (normalisation+verb patterns) + C5 real few-shot + wire persona.yaml or delete. 2. C1 token counting/budget + M5c per-provider max_completion_tokens (Groq 1500-2000, Gemini 4000) + include_reasoning=False. 3. C3+C4 grounding v2 top-3, skip video hosts, pass URLs, require citations, widen unknown markers, abstain-in-character when still ungrounded. 4. C6 memory speaker-tagged history, persist mood decay once, implement notes/pinned_facts or drop, praise detection. 5. M1+M2 structured BotPlan + search-only judge. M3 rolling summary. RAG last after live group test.
