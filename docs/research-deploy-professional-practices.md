# Research: what professionals do when deploying a Telegram bot in production (2026-11-25)

10 web searches (Telegram Bot API docs, python-telegram-bot v22.8 docs, Render/Oracle docs, engineering blogs, GitHub production examples). Read-only.

## 1. Webhook vs long-polling
Mutually exclusive per token. While a webhook is set, `getUpdates` fails with `409 Conflict`; two processes polling the same token also hit 409. Updates are held on Telegram's servers for at most 24 hours in either mode.
- Long polling: bot pulls (outbound HTTPS only), no public HTTPS URL needed, works behind NAT/firewall/laptop, one poller per token.
- Webhook: Telegram pushes HTTPS POST per update; needs public HTTPS on ports 443/80/88/8443, TLS 1.2+; allows multiple instances behind a load balancer.
- Webhook requirements: public HTTPS endpoint; `secret_token` (1–256 chars) so Telegram sends `X-Telegram-Bot-Api-Secret-Token` on every request — handler must compare it and return 403 on mismatch (Telegram does not sign the body; the header is the only authentication). Handler must answer **2XX immediately and do the work afterwards** — any other status makes Telegram retry the update, and a slow handler doing LLM work before responding produces duplicate processing. `getWebhookInfo` is the read-back: empty `url` means polling mode; growing `pending_update_count` means deliveries are failing. `max_connections` defaults to 40 (max 100). Switching modes is a live operation: `deleteWebhook` accepts `drop_pending_updates` — dropping is correct after a long outage for a chat bot, wrong for a payment bot.
- **Is polling unprofessional? No — for a 15-user bot it is the recommended choice.** Consensus across 2026 guides: "For one bot on one server, go with long polling: it's simpler and no slower. A webhook pays off when you need several instances and zero-pause deploys, when you run many bots, or when the bot already has a web part such as a Mini App." (forestsnet.cloud, Sep 2026). "If polling already works on your machine, keep it." (telegram-bot-api.info, Nov 2026). "For most small bots, start with polling and switch only when a public HTTPS delivery path solves a real requirement." (macmyths.com). Telegram's own webhook guide says the CPU/latency gains "depend heavily on the usage pattern of your bot. Measure before you migrate." One dissenting voice (telegraft.dev) calls polling "a development tool" — but its argument is about scale and serverless, which do not apply to a single-instance 15-user bot.
- Bottom line: polling is fine and is what the pros pick for one bot on one always-on process. Webhook becomes mandatory only if the host is serverless or if you need horizontal scaling. The bot's existing `run_polling(timeout=30, drop_pending_updates=..., bootstrap_retries=-1)` is the standard shape; the one thing to fix when deploying as a Render web service is `drop_pending_updates=False` so sleep-induced backlogs are delivered, not silently discarded.

## 2. Deployment shape: Docker vs systemd vs PaaS vs serverless
- **Docker container (Compose) — the professional default for a single bot.** "The simplest reliable deployment is a single Compose service running a pinned Python image and python-telegram-bot in polling mode, with the Telegram token mounted as a Compose secret and `restart: unless-stopped` enabled. Add a named volume only for state that must survive container replacement." (macmyths.com). Dockerfile rules: exec-form `CMD` (shell form makes `/bin/sh` PID 1, which swallows SIGTERM), pinned base image, token passed at runtime with `--env-file`, never baked into the image, `.env` in `.dockerignore` and `.gitignore`.
- **systemd on a VPS — the simplest thing that works.** A polling bot managed by systemd "is usually enough" for a simple project/personal bot/MVP. Unit: dedicated system user without shell/sudo, code under `/srv` or `/opt`, venv, token in `/etc/mybot.env` (mode 0600), `Restart=on-failure`, `RestartSec`, logs via `journalctl`. Pros: zero platform abstraction, full control, real disk (SQLite survives), no sleep, no hour caps. Cons: you own patching, firewall, monitoring. For this bot, systemd + Docker Compose on an Oracle Always Free VPS is the same deployment the bot already has locally, with a named volume for `data/bahgat.db`.
- **PaaS (Render / Railway / Fly.io) — convenient, but the free tier fights a polling bot.** Render: free only for web services, 512 MB / 0.1 CPU, spins down after 15 min idle, ~1 min wake, 750 free hours/month shared by the workspace, 5 GB bandwidth/month, no persistent disk, free Postgres expires after 30 days. Railway: Hobby $5/month, free plan $1/month of usage, app sleeping after 5–10 min idle — but a polling worker sends outbound packets constantly, so it stays awake. Fly.io: no free tier for new accounts, $1 trial credit for 7 days, then pay-per-use from ~$2.19/month. PaaS trade-off: deploys/rollbacks/logs are one click and git-push driven, but you inherit sleep, hour caps, ephemeral disks, and per-service pricing that makes a worker + database + monitoring cost $25–86/month on Render vs ~$7 on a 4 GB server.
- **Serverless (Workers / Lambda / Cloud Run) — wrong shape for this bot.** A function cannot hold a long poll open between invocations, so webhook mode is mandatory; and this bot's media pipeline (yt-dlp + ffmpeg, Edge TTS → Opus) cannot run there at all. Cloud Run additionally scales to zero when idle and enforces request timeouts (default 5 min). Serverless fits stateless webhook bots; it does not fit a polling bot with local media processing.
- Trade-off summary: restarts — systemd/Docker `restart: unless-stopped` and PaaS both auto-restart on crash; logs — `journalctl`/`docker logs` vs PaaS dashboard (Render free has no SSH/shell); updates — `git pull` + rebuild vs git-push deploy vs `systemctl restart`; rollbacks — PaaS keeps the last 2 deploys, Docker/systemd roll back by re-pulling the previous image/tag. For a 15-user hobby bot the differences that matter are: (a) does the disk survive a restart (VPS yes, Render free no), (b) does the process sleep (VPS no, Render free yes), (c) who patches the OS (you on a VPS, the platform on PaaS).

## 3. Secrets management
Universal rule: config in the environment, never in code (Twelve-Factor App, Factor III). Never commit `.env` (once a secret is in git history it is compromised even if deleted later — GitHub detected 39 million secret leaks in public repos in 2024; 70% of secrets leaked in 2022 are still active per GitGuardian 2025); always commit `.env.example` with placeholder values; never log credentials; use different credentials per environment.
- Solo/small project (this bot): platform-managed env vars — Render/Railway/Fly dashboard or CLI. Values live in the platform, injected at runtime, never touch the repo. Locally, a `.env` file (gitignored) loaded at startup.
- Teams/CI: GitHub Actions secrets / GitLab CI variables, injected as env vars at deploy time.
- Larger orgs: dedicated secret manager (HashiCorp Vault, AWS Secrets Manager, Doppler, Infisical) — explicitly overkill for this bot.
- Validation: fail fast at startup if a required variable is missing; use typed settings (`pydantic-settings` with `SecretStr`) rather than raw `os.getenv()`.
- Safe way to get this bot's 4 keys into a free host: paste each key once, by hand, into the host's own env-var UI — Render dashboard → service → Environment (TELEGRAM_BOT_TOKEN, GEMINI_API_KEY, GROQ_API_KEY, NVIDIA_API_KEY); on an Oracle VPS, a root-only file `/etc/bahgat.env` (mode 0600) referenced by `EnvironmentFile=` in the systemd unit or `--env-file` for Docker. Never in `render.yaml`, the Dockerfile, `docker-compose.yml`, or any file committed to git. If a key is ever committed or pasted in chat by mistake, rotate it immediately (Telegram: revoke via BotFather; Groq/Gemini/NVIDIA: regenerate in the console) — deleting it from history is not enough. Keys stored in Muse's Secure Vault are **not** available to a deployed process — the owner must paste them into the host himself.

## 4. Reliability: essential vs nice-to-have vs overkill at this scale
**Essential:**
- **Single-instance guard — no double polling.** One running instance per token. Two pollers split updates and keep hitting 409 Conflict. On Render: `numInstances: 1` (already set); never run a local test poller against the production token while the deployed bot runs (use a second bot token for local dev). For webhook bots the equivalent is idempotency on `update_id`, which this bot already has (durable `processed_updates` table).
- **Graceful shutdown.** Every deploy/restart ends with SIGTERM, then a grace period, then SIGKILL (Docker `stop` 10 s, systemd 90 s, Kubernetes 30 s). Recipe: stop accepting new work → let in-flight handlers finish (with a timeout) → flush logs, close the database, commit queue acks → exit 0. python-telegram-bot handles this: `run_polling()`/`run_webhook()` listen for SIGINT/SIGTERM/SIGABRT by default and run the `post_shutdown` hook (close the DB there). Trap: Dockerfile shell-form `CMD python -m bot.main` makes `/bin/sh` PID 1, which may not forward SIGTERM — use exec-form `CMD ["python", "-m", "bot.main"]`. This bot already has graceful shutdown + heartbeat file + `HEALTHCHECK` in its Dockerfile.
- **Health endpoint + uptime monitoring.** A tiny HTTP endpoint (`/health`, returns 200 + a heartbeat timestamp) is what lets a PaaS know the service is alive and what lets an external monitor detect death. UptimeRobot free tier: 50 monitors, 5-minute checks, email/Telegram alerts — the standard free choice. On Render the same pinger doubles as the keep-alive that defeats the 15-minute spin-down. A dead-man's-switch variant (Healthchecks.io) alerts when a periodic job *doesn't* check in — useful for the nightly backup, not for the bot itself.
- **Backups of state.** State *is* the product (per-member memory, moods, grudges, quotas, response cache). SQLite + WAL is production-ready for single-server moderate traffic. Professional pattern is Litestream: a sidecar that continuously streams WAL changes to S3-compatible storage (Cloudflare R2 free tier: 10 GB) with ~1 s replication and point-in-time restore, plus a nightly `backup-db.sh` tarball as a second, RPO-24 h fallback. Minimum viable version: a nightly cron that copies `bahgat.db` (via SQLite's online backup API or `VACUUM INTO`) to R2, with a restore-on-boot step. Untested backups are the classic failure — run a restore drill to `/tmp` and `PRAGMA integrity_check` at least once.
- **Respect Telegram's flood limits.** ~1 message/second per chat, ~20 messages/minute per group, ~30 messages/second globally per bot; exceeding them returns HTTP 429 with `parameters.retry_after`. Only correct response is to wait exactly `retry_after` seconds and retry. This bot already has per-chat pacing (1 reply/user/10 s), a per-chat in-flight lock, and `RetryAfter` handling; a per-chat FIFO outbox queue is the pro pattern for broadcast-heavy bots and is overkill here.
**Nice-to-have (do later, cheap):** log-based alerting (structured JSON logs — this bot already emits one per LLM call — + alert on error-rate spikes or 429 storms; without a log aggregator, the practical version is Render dashboard log stream + UptimeRobot down-alerts). Zero-downtime updates: for polling bots this means stop-first deploys; rolling deploys are only safe for webhook bots. At 15 users, a 30–60 s restart window with updates queued on Telegram's side for 24 h is fine — the bot just needs `drop_pending_updates=False`. Dependency pinning + lockfile (this bot already pins PTB; CI runs ruff + pytest).
**Overkill (do not build):** Kubernetes, multi-instance/load-balanced deployment, autoscaling (bot is single-instance by Telegram's own design). Redis/Postgres cluster, message queue (Celery/RabbitMQ), or a separate worker tier — SQLite + WAL + one process handles this volume with orders of magnitude to spare. Full observability stack (Prometheus/Grafana/Sentry/PagerDuty) — UptimeRobot + structured logs + `/stats` cover it. Staging environment with a second bot — test in the existing private test group with the production bot. Blue/green or canary deploys, feature flags, chaos testing.

## 5. Cost control on free tiers
- **Render:** 750 free instance hours/month per workspace, shared by all free web services — one service awake 24/7 consumes 744 h in a 31-day month; run out and *every* free service is suspended until the 1st. Bandwidth now 5 GB/month included (cut from 100 GB in Apr 2026), then $0.15/GB — without a card on file, running out suspends free services for the rest of the month. Render's docs warn free web services "may be suspended" for "uncommonly high volume" of service-initiated outbound traffic (external APIs/databases/object storage) — a Telegram bot that calls Groq/Gemini/NVIDIA on every message is exactly that shape, so the risk is real and the only remedy Render offers is moving to a paid plan. Also: free web services can't receive private-network traffic, can't use persistent disks or SSH, and "Render might restart a Free web service at any time." The $7/month Starter plan (0.5 CPU/512 MB, never sleeps) is the universally cited first money worth spending.
- **Oracle Always Free:** 2 OCPU / 12 GB ARM (halved from 4/24 GB in June 2026), 200 GB block storage, 10 TB egress, no expiry — but Oracle "may reclaim" instances deemed idle: over a 7-day period, 95th-percentile CPU < 20% **and** network < 20% **and** (A1 only) memory < 20%. A quiet bot can trip this; documented mitigations are running a small enough instance that used RAM exceeds 20%, or a CPU keepalive — which sits in a gray area under Oracle's terms (neither explicitly allowed nor forbidden; the FAQ warns non-compliance "may result in suspension or termination"). Other traps: A1 capacity is often "out of host capacity" (retry another availability domain / smaller shape / different time of day); card + phone verification required (prepaid/virtual cards often refused); home region is chosen once at signup and cannot change; trial-end cleanup deletes paid resources created with the $300 credit if you exceed Always Free shapes.
- **General free-tier discipline:** keep everything inside one workspace/account so hours/quotas are visible in one place; watch the monthly usage page (Render emails at ~80% and at exhaustion); put a hard cap on the expensive dimensions (this bot's dynamic fair-share quota already does this for LLM tokens); avoid a second always-on service (pinger, dashboard) that would consume the same 750-hour budget; never let a runaway loop (retry storm, unbound yt-dlp download) burn bandwidth/CPU — circuit breakers, per-call timeouts, and the 50 MB download cap already in this bot are the right shape.

## Recommendation for THIS bot
**Keep polling. Deploy as one Docker container with a named volume for `data/`, behind systemd (or Compose `restart: unless-stopped`) on an Oracle Always Free VPS as the final home; use Render as a free web service only as a stopgap.** Concretely: (1) Polling (`run_polling`, `drop_pending_updates=False`) — webhook buys nothing at 1 instance / 15 users and costs a domain, TLS, a secret-token check, and a rewrite of the media path. (2) Secrets: paste the 4 keys once into the host's env-var store (Render dashboard, or `/etc/bahgat.env` mode 0600 on the VPS). Never in git, never in the image. (3) Essential reliability, all cheap: exec-form CMD + PTB's built-in SIGTERM handling, single instance, `/health` endpoint + UptimeRobot free monitor (5-min checks, doubles as Render keep-alive), nightly SQLite backup to R2 with a restore drill, `RetryAfter` honoured everywhere. (4) Cost control: one service only on Render (750 h budget); on Oracle, keep the instance visibly non-idle and back up the DB off-VM so a reclaim is an annoyance, not a data loss. (5) Skip: Kubernetes, Redis, queues, Sentry, staging bots, multi-instance. The first money worth spending if free ever breaks is Render Starter $7/month (no sleep, no hour cap, persistent disk).
