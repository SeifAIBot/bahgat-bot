# Research: Render vs Cloudflare for the Bahgat bot — free tiers only (2026-11-25)

Independent web research (read-only). Bot: Python 3.12, python-telegram-bot, long-polling (NOT webhooks), SQLite, yt-dlp (up to 50 MB, needs disk + ffmpeg), Edge TTS voice notes (needs ffmpeg), Docker image, render.yaml already exists (Render Background Worker, numInstances 1), one always-on process 24/7, ~15 users, low traffic.

## 1. Render free tier in 2026
- One workspace gets **750 free instance hours/month**, 512 MB RAM, ~0.1 CPU, 500 build minutes/month, 100 GB bandwidth, no card required. A 31-day month has 744 hours, so the allowance covers exactly **one** service running around the clock and nothing else. When hours run out, **every** free service in the workspace is suspended until the 1st of next month.
- **Free plan does not cover background workers at all.** Per Render's Blueprint spec, the `free` instance type "is not available for private services, background workers, or cron jobs" — only web services and static sites accept `plan: free`. A `render.yaml` declaring `type: worker` + `plan: free` does not deploy; the Blueprint fails validation. The bot's existing `render.yaml` (Background Worker) **cannot deploy on free as written** — it must become a web service, which means it must bind a port (Render fails the deploy if nothing listens on `0.0.0.0`), and it sleeps.
- **Sleep:** free web service spins down after **15 minutes without inbound traffic**, takes ~30–60s to wake. For a long-polling bot the bot is deaf while asleep: it stops calling `getUpdates`. Telegram holds undelivered updates up to 24h, so messages are delayed, not lost — **unless** the bot wakes with `drop_pending_updates=True` (which v0.5 set), in which case everything sent during the sleep is silently discarded. Fixes: keep it awake with an external pinger every ~10 min (UptimeRobot / cron-job.org hitting the health endpoint — costs ~730 of the 750 monthly hours, i.e. the whole allowance), or set `drop_pending_updates=False` and accept a burst of stale messages on wake.
- **Ephemeral disk — the real problem.** Free services have an **ephemeral filesystem**: every redeploy, restart, or spin-down wipes the disk back to the repo state. No persistent disks on the free tier (paid-only). So `data/bahgat.db` — per-member memory, moods, grudges, quotas, response cache — is **deleted on every redeploy**. Render may also restart a free service at any time. Render's own free Postgres is not a fix: 1 GB, no backups, **expires 30 days after creation** (14-day grace, then deleted). A polling bot is otherwise a normal supported use case on Render; docs warn "do not use them for production applications."

## 2. Cloudflare free tier in 2026
- Workers Free: **100,000 requests/day**, **10 ms CPU time per invocation** (HTTP and Cron Triggers alike), 50 subrequests per invocation. CPU time is compute only — waiting on `fetch()`, KV, or D1 does not count. Python Workers are now **generally available** (Pyodide-based, Python 3.12+, any Pyodide-compatible package, FastAPI/Django/Flask runnable).
- **Long polling is impossible on Workers.** A Worker runs only while handling a request; no persistent process, no background loop, no `sleep()`. The bot would have to switch to **webhook mode** (`setWebhook`): Telegram POSTs each update to the Worker's public HTTPS endpoint. Webhook and polling are mutually exclusive. The `python-telegram-bot` `Application` + `run_polling` architecture would be replaced by a thin webhook handler that parses the update JSON and calls the bot logic directly; polling machinery, job queue, and updater all go away.
- **What breaks:** YouTube downloads — dead (no subprocesses, no binaries, no writable local filesystem; yt-dlp and ffmpeg cannot run; would need a separate service or be dropped). Voice notes — dead as built (Edge TTS audio is MP3; Telegram voice notes need OGG/Opus, which requires ffmpeg; no voice on Workers unless TTS is offloaded to an external API returning Opus directly). Local SQLite — must be rewritten: D1 is SQLite-*compatible* SQL over an HTTP binding, not a local file. Every `sqlite3` call becomes a D1 API call (async, 50 queries per invocation on Free). D1 Free: **5M rows read/day, 100k rows written/day, 5 GB total, 10 DBs, 500 MB per DB**, quotas reset 00:00 UTC, and since 1 Sep 2026 queries **fail** once the daily quota is hit. For this bot's volume D1's quotas are comfortable — the cost is the rewrite, not the limits.
- **10 ms CPU per invocation is the tightest constraint.** A webhook handler that mostly waits on LLM APIs spends little CPU, so it can fit — but all per-message Python work (Arabic normalisation, intent detection, prompt building, insult filtering, quota math) must complete in 10 ms of Pyodide CPU. Plausible, not guaranteed.
- Workers AI (10,000 neurons/day) is irrelevant except as a curiosity: the bot already calls Groq/Gemini/NIM via plain `fetch`.
- Cron Triggers (5 per account on Free, also 10 ms CPU) cannot substitute for polling: a cron invocation can't hold a 30s `getUpdates` long-poll.
- **What the Cloudflare path would take:** webhook handler + D1 migration of all persistence + re-implementing the `python-telegram-bot` dispatch by hand + dropping or offloading yt-dlp/ffmpeg. Roughly **3–5 days of focused work**, and two headline features (YouTube downloads, voice notes) die unless a second host is added for media — at which point "free Cloudflare" is really "Cloudflare + something else".

## 3. Third options, one line each
- **Oracle Cloud Always Free VPS:** 2 OCPU / 12 GB ARM (halved June 2026), 200 GB block storage, 10 TB egress, no expiry, never sleeps — bot runs as-is (Docker/systemd), SQLite survives on disk; catch is card verification, a capacity lottery for provisioning, Linux self-management, and Oracle may reclaim instances idle 7+ days.
- **Fly.io:** no free tier for new accounts — trial only ($1 credit / 7 days), then pay-per-use from ~$2.19/month. Not free.
- **Railway:** $5 one-time trial credit for 30 days, then $1/month — not enough for a 24/7 process.

## 4. Recommendation for THIS bot
**Deploy on Render now — but as a free web service, not a background worker.** Only option that runs the bot with zero code rewrite: Docker image, `python-telegram-bot`, SQLite, yt-dlp, ffmpeg all work unchanged. Required changes are small: change `render.yaml` to `type: web` + `plan: free`, add a tiny HTTP health endpoint that binds `$PORT`, and add an external pinger (every 10 min) to keep it awake inside the 750-hour budget — or accept sleep and set `drop_pending_updates=False`.
- **Honest trade-offs of Render:** SQLite wipes on every redeploy/restart — the one serious flaw (the bot's personality *is* its memory). Mitigations in order of effort: (a) **nightly backup** of `bahgat.db` to Cloudflare R2 free tier (10 GB) with restore-on-boot — ~1 hour of work, survives redeploys but loses up to a day of memory; (b) **migrate state to Neon free Postgres** (1 GB/project, ~100 CU-hours compute, no expiry — unlike Render's own free Postgres) — the proper fix, roughly a day of work rewriting the SQLite layer; (c) accept the wipes — bad, do not do this.
- **512 MB RAM / 0.1 CPU** is tight for yt-dlp + ffmpeg: a 50 MB download and transcode will be slow (minutes) and can stall other replies while it runs; the per-chat in-flight lock already serialises this, so it degrades gracefully rather than crashing.
- **One service consumes the whole free allowance.** A second free service would exhaust the 750 hours mid-month and suspend everything.
- **The $7/month Starter escape hatch** fixes all of it at once: no sleep, no hour cap, persistent disks. If the bot proves popular, that is the first money worth spending.
- **Cloudflare is the wrong move for this bot today.** Better platform in the abstract (no sleep, generous request budget, durable D1), but demands a 3–5 day rewrite and kills the two features that make the bot fun (YouTube, voice). It only makes sense later if the bot outgrows Render *and* someone rebuilds the media pipeline elsewhere.
- **Long-term note:** if the goal is "free forever, no wipes, no rewrites", **Oracle Always Free** is the best final home — the bot runs there exactly as it runs locally, with a real disk. Costs a day of Linux setup and a card verification — a weekend migration, not today's deploy. Sequence: Render now (today) → Neon or R2 backup for memory safety (this week) → Oracle later if Render's sleep/restarts become annoying.
